# Auth stack

Стек аутентификации с gRPC-сервисом на Go и PostgreSQL. Код сервиса находится в каталоге `auth-service`.

Поддерживает регистрацию, вход, ротацию refresh-токенов и выход. Пароли хешируются с помощью Argon2id. Access-токены — JWT с подписью HS256; refresh-токены — случайные секретные строки, которые хранятся в БД в виде SHA-256-хешей.

## API

Контракт описан в [`proto/auth/v1/auth.proto`](auth-service/proto/auth/v1/auth.proto).

| RPC | Запрос | Результат |
| --- | --- | --- |
| `SignUp` | UUID `id`, email, пароль и подтверждение пароля | Пара токенов и их TTL |
| `LogIn` | Email и пароль | Пара токенов и их TTL |
| `Refresh` | Refresh-токен | Новая пара токенов и их TTL |
| `LogOut` | Refresh-токен | Пустой ответ при успехе |

TTL в ответах указан в секундах.

Каждый вход создаёт отдельную сессию. При обновлении предъявленный refresh-токен помечается использованным, а новый привязывается к той же сессии. Повторное предъявление использованного токена отзывает сессию. Блокировка сессии и изменения токенов выполняются в транзакции PostgreSQL.

Сессия имеет фиксированный максимальный срок действия. Срок новых токенов ограничивается оставшимся временем сессии. Выход отзывает сессию и запрещает дальнейшее обновление токенов. Уже выданный access JWT может оставаться действительным до своего истечения.

Бэкенды с защищёнными данными проверяют access JWT и применяют собственные правила авторизации. Refresh-токены передаются только сервису аутентификации.

## Запуск через Docker Compose

Файл `compose.yml` находится в корне репозитория. Выполните следующие шаги из корня:

1. Создайте `.env` с переменными `DB_NAME` и `DB_USER`, например:

   ```dotenv
   DB_NAME=auth_db
   DB_USER=auth_admin
   ```

2. Создайте файлы `secrets/db_password` и `secrets/jwt_secret`. Используйте надёжный пароль БД и криптографически случайный секрет подписи JWT длиной не менее 32 байт.
3. Запустите стек:

   ```sh
   docker compose up --build
   ```

Compose запускает PostgreSQL, применяет миграции, затем запускает сервис на `127.0.0.1:50051`. Данные PostgreSQL сохраняются в томе `pgdata`.

Сейчас сервер использует gRPC без TLS. Такая конфигурация предназначена для локальной разработки. Перед внешним доступом настройте TLS на сервере или доверенном прокси.

## Конфигурация

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `GRPC_ADDR` | `:50051` | Адрес прослушивания |
| `DB_USER` | Обязательная | Пользователь PostgreSQL |
| `DB_NAME` | Обязательная | Имя базы данных |
| `DB_HOST` | Обязательная | Хост PostgreSQL |
| `DB_PORT` | `5432` | Порт PostgreSQL |
| `DB_PASSWORD_FILE` | Обязательная | Путь к файлу с паролем БД |
| `DB_OPTIONS` | Не задана | Параметры подключения, например `sslmode=disable` локально |
| `JWT_SECRET_FILE` | Обязательная | Путь к файлу с секретом подписи JWT |
| `ACCESS_TOKEN_TTL` | `15m` | Срок действия access-токена |
| `REFRESH_TOKEN_TTL` | `720h` | Срок действия refresh-токена: 30 дней |
| `SESSION_TTL` | `2160h` | Максимальный срок сессии: 90 дней |

Длительности задаются в формате Go, например `15m` или `720h`. Запись `30d` не поддерживается.

Для запуска без контейнера перейдите в `auth-service`, затем примените миграции, задайте переменные окружения и выполните `go run .`. Версия Go указана в `go.mod` — сейчас `1.27.3`.

## Тесты

Интеграционные тесты запускают PostgreSQL через Testcontainers и применяют миграции. Docker должен быть запущен и доступен текущему пользователю.

Из корня репозитория сначала перейдите в каталог сервиса:

```sh
cd auth-service
go test -v -count=1 -tags=integration ./internal/usecase
```

Текущие сценарии проверяют вход с несуществующей учётной записью, успешную ротацию и отказ при повторном предъявлении использованного refresh-токена. Тесты вызывают use case с реальными адаптерами БД; транспорт gRPC ими не проверяется.

Файлы с тегом `integration` не включаются в обычный запуск:

```sh
go test ./...
```

## Генерация кода

Команды генерации выполняются из каталога `auth-service`. Сгенерированные файлы хранятся в репозитории. После изменения SQL-запросов или миграций обновите код доступа к БД:

```sh
sqlc generate
```

После изменения Protobuf-контракта запустите `protoc`. Утилиты `protoc-gen-go` и `protoc-gen-go-grpc` должны быть доступны через `PATH`:

```sh
protoc -I proto -I /usr/include \
  --go_out=proto/gen --go_opt=paths=source_relative \
  --go-grpc_out=proto/gen --go-grpc_opt=paths=source_relative \
  auth/v1/auth.proto
```

Замените `/usr/include`, если файл `google/protobuf/empty.proto` находится в другом каталоге вашей системы.

## Структура проекта

Пути ниже указаны относительно `auth-service/`:

```text
internal/domain/             Пользователи, сессии и refresh-токены
internal/usecase/            Сценарии аутентификации и интерфейсы зависимостей
internal/adapter/handler/    gRPC-обработчики и преобразование ошибок
internal/adapter/auth/       Подпись и проверка JWT
internal/adapter/store/pgx/  Репозитории и менеджер транзакций
internal/pkg/               Конфигурация, интерсепторы и инфраструктурные функции
migrations/                 Миграции схемы PostgreSQL
sqlc/                       Исходные SQL-запросы
proto/                      Protobuf-контракт и сгенерированный Go-код
```
